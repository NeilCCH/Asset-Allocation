# 合規架構 — 資料流向與隔離(最高優先)

本文件說明系統如何在**架構層**落實 PRD §1 的合規約束。開發任何功能前先讀。

## 核心原則

1. **系統不對客戶推介。** 演算出的「配置面向建議」只存在 `advisor_private` 表,只在顧問後台呈現。
2. **不推介單一商品。** 系統輸出只到「資產類別 / 配置面向」層級,不出現標的名稱、代號、買賣指示。
3. **對客戶的建議由「人」產出。** 系統是決策輔助;推介主體是**具專業資格的顧問本人**(註冊時登錄證照佐證)。
4. **缺口試算為透明、可調參數的客觀公式**(見 `src/lib/domain/calc.ts` + `params.ts`),不含投資意見。
5. **PDPA 同意閘門**內建於客戶填寫流程最前端。

> 個人業務員資格 ≠ 公司投顧營業執照。系統**自動**推配置建議給客戶仍屬機器人理財(事業體特許),不因個人證照而放行。最終以公司法遵簽核為準。

## 三層資料的可見性(由 RLS 物理強制)

| 資料 | 資料表 | 客戶可見 | 顧問可見 |
|------|--------|:---:|:---:|
| 問卷作答 | `questionnaire_responses` | ✅ 自己 | ✅ 名下客戶 |
| 彙整**事實層**(資產分布、保障vs投資、缺口概況) | `client_summaries` | ✅ 自己 | ✅ 名下客戶 |
| **配置面向建議** + leads A/B/C 評分 + 顧問建議草稿 | `advisor_private` | ⛔ **永不** | ✅ 名下客戶 |

## 為什麼客戶「物理上」讀不到 advisor_private

`advisor_private` 啟用 RLS 後,**只**建立「綁定顧問可讀寫」的 policy,**刻意不建立**任何客戶可讀的 policy。RLS 預設拒絕 → 客戶以 anon key + 自身 session 查詢本表一律回傳 0 rows。這不是應用層 if-else 可繞過的約定,是資料庫層強制。

## 開發守則

- 客戶端頁面 / API **不得** import `src/lib/domain/leads.ts`,不得查詢 `advisor_private`。
- 彙整運算(寫 `client_summaries`)以 service_role 於伺服器端執行,只寫入事實層欄位。
- leads 評分與配置框架的產生,只發生在顧問後台的伺服器端路徑。
- 配置框架採「**顧問手動勾選、系統只提供參考框架**」,不做規則庫自動產生(降低自動化投顧疑慮)。
